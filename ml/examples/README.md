# CPU 재현용 입력 예제

`input.json`은 실제 원본 행으로 만든 작은 과거 재현 입력입니다. `predict()`를 직접 호출하는 샘플이며, 현재 웹 API에 그대로 넣는 요청 본문은 아닙니다. 실행 방법과 CPU 비교 허용 오차는 [상위 README](../README.md)를 따릅니다.

| 파일 | 용도 |
| --- | --- |
| `input.json` | 실제 판매 56일 × 상품 2개와 과거 날씨 57일을 포함한 정상 입력 |
| `expected-quantiles.json` | 같은 입력의 CPU 7일 × 5분위수 기준 출력 |
| `expected-api.json` | 같은 입력의 API용 3분위수 출력 |
| `expected-insufficient-history.json` | 부족 이력 및 신규 상품 입력의 예상 결과 |
| `cpu-verification.json` | 별도 빈 환경의 설치 후 CPU 실행 측정 |
| `input-fields.json` | 현재 API에 추가할 필드의 이름·단위·예시·검증 규칙과 SI 입력 예시 |
| `insufficient-history.json` | 한 상품의 판매일을 하나 제거하고 미등록 상품을 추가한 실패/성공 혼합 입력 |

이 디렉터리의 예상 출력은 동일 입력과 기존 체크포인트를 CPU에서 실행해 생성합니다. `predict_quantiles()`의 검증용 출력은 7일 × 5분위수 `[0.10, 0.25, 0.50, 0.75, 0.90]`를 보존하고, API용 `predict()`는 각 날짜에 `date`, `p10`, `p50`, `p90`만 반환합니다.

## 정상 샘플의 출처

- 원본: Walmart Recruiting II: Sales in Stormy Weather의 `train.csv`, `weather.csv`, `key.csv`.
- 학습 실행: `walmart_20261024T020058Z`의 `selected_series.csv`에 등록된 매장 `4`, 상품 `9`와 `27`, 관측소 `9`.
- 애플리케이션 식별자: `store_id="walmart-demo-4"`, 상품 ID `walmart-9`, `walmart-27`. 상품명은 익명 원본 번호를 표시하는 데모 이름이며 실제 상품명·한국 상품과의 대응을 의미하지 않습니다.
- 기준일: `2014-09-12`. 판매 입력: `2014-07-19`~`2014-09-12`, 상품마다 연속 56개 **실제 관측 행**. 판매가 없는 날을 임의로 0으로 추가하지 않았습니다. 원본의 관측된 0은 그대로 유지합니다.
- 예측 날짜: `2014-09-13`~`2014-09-19`, 저장된 테스트 예측의 동일 기준일에 해당합니다. 샘플은 재현 확인용이며 두 상품만으로 전체 성능을 평가하지 않습니다.
- 날씨 입력: 관측소 `9`의 `2014-07-18`~`2014-09-12`, 57개 원본 관측 행. 인코더 시작 전 하루를 포함했으며 그 날의 다섯 기상 값이 모두 관측되어 전체 원본의 인과적 전방 채움과 같은 초기 상태를 제공합니다.
- 강수 원문 `T`를 `2014-08-09`, `08-26`, `08-27`, `09-08`에 보존했습니다. 전처리에서 강수량은 0, `precip_trace`는 1이 됩니다. 나머지 숫자 문자열은 JSON 숫자로 바꾸었으며 값과 단위는 유지했습니다.
- 기준일 이후 판매량이나 실제 날씨는 입력하지 않았습니다. 예측기의 미래 날씨는 학습 때와 동일하게 처리된 기준일 날씨를 7일 반복하는 `persistence`입니다. 당시 발급된 실제 일기예보를 이용한 입력이 아닙니다.

## API에서 추가로 필요한 값

실제 이름·단위·예시가 들어 있는 [input-fields.json](input-fields.json)을 API 확장 명세로 사용합니다. 현재 context에 없는 학습용 식별자와 과거 날씨를 `model_input`에 명시하고, 상품마다 `model_item_nbr`를 둡니다. `time_idx`, 달력 특징, 결측 플래그, trace 플래그는 전처리가 계산하므로 API가 전송하지 않습니다.

| 필드 | Walmart 원본 단위 | `weather_units="si"`일 때 단위 |
| --- | --- | --- |
| `tavg`, `tmax`, `tmin` | °F | °C |
| `preciptotal` | inch/day | mm/day |
| `avgspeed` | mph | m/s |
| `sales[].units_sold` | 일별 판매 개수, 정수 | 동일 |

열 이름은 SI에서도 같습니다. 변환은 `°F=°C×9/5+32`, `inch=mm/25.4`, `mph=(m/s)/0.44704`입니다. 일평균 기온 `tavg`나 일평균 풍속 `avgspeed`가 없으면 null로 표시합니다. 최고·최저 기온으로 일평균을 임의 계산하거나 풍속 대신 돌풍을 넣지 않습니다. 원본 `M`은 결측, `T`는 trace를 뜻하며 `T`는 원본 Walmart 기록에만 사용합니다.

기상 결측은 특징별 플래그를 먼저 만들고 동일 관측소의 과거 값으로 전방 채움한 뒤, 채울 과거 값이 없으면 **저장된 학습 구간 중앙값**을 사용합니다. 이때 과거 날씨가 관측되지 않았다는 플래그는 그대로 남습니다. 56일 창의 첫날에 결측이 있으면 그보다 이전의 마지막 관측까지 포함해야 원본 전체 전처리의 전방 채움을 정확히 재현합니다.

`weather`의 출처 표시는 `status="ok"`, `mode="historical_observations"`, `source="Walmart Stormy Weather"`입니다. 수집 시각을 확인할 수 없어 `fetched_at=null`입니다. 현재 API의 날씨 사용 모델은 `live_forecast`만 허용하므로 이 과거 데모는 API 담당자가 명시적인 데모 경로를 마련해야 합니다. 과거 관측값을 실시간 예보로 이름만 바꾸면 안 됩니다. 이 체크포인트는 `weather.days`의 미래 예보를 사용하지 않습니다.

## 이력 부족과 신규 매장·상품

`insufficient-history.json`은 정상 입력을 복사한 뒤 다음 두 가지를 바꾼 완전한 실행 입력입니다.

1. `walmart-9`의 `2014-08-01` 판매 관측을 삭제했습니다. 반환은 `status="insufficient_history"`, `points=[]`, 55/56일 설명이어야 합니다.
2. `model_item_nbr`가 없는 `new-product`를 추가했습니다. 반환은 `insufficient_history`, `points=[]`, 명시적인 학습 상품 대응이 없다는 설명이어야 합니다.

`walmart-27`은 정상 입력과 같은 7일 예측을 계속 반환해야 합니다. 알려진 매장·상품 조합에 필요한 56일이 없거나 새 매장·상품 조합이 저장된 학습 대상에 없으면 임의 예측을 생성하지 않습니다. 한국 매장이나 상품을 번호가 비슷한 Walmart 개체에 매핑하지 않습니다. 신규 개체는 실제 데이터를 별도로 수집하고 새 모델·인코더를 학습 및 평가한 뒤 해당 아티팩트로 등록해야 하며, 요청 중 학습하거나 fit하지 않습니다.

원본 학습 노트북의 성능평가에는 관측되지 않은 판매일을 `sales_observed` 마스크로 처리하는 희소 패널도 포함됩니다. 서버 어댑터는 인수 규약에 맞춰 최근 56일 판매를 모두 요구하므로, 원본 평가에서 사용된 모든 기준일이 서버의 정상 예측 대상으로 통과하는 것은 아닙니다. 이 샘플은 그 차이를 피하기 위해 실측 56일이 존재하는 매장·기준일을 골랐습니다.
