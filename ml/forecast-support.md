# 실제 발급 예보를 사용하는 TFT의 지원 조건

## 현재 확인된 동작

현재 체크포인트와 [preprocess.py](preprocess.py)는 `weather_strategy="persistence"`만 지원한다. 기준일까지 관측된 날씨를 전처리한 뒤 마지막 날의 특징을 미래 7일에 반복한다. 학습·검증·테스트에서 사용한 방법도 같다. 과거 실측 날씨를 사용한 역사적 재현이며, **당시 발급된 실제 일기예보로 학습하거나 평가한 모델이 아니다.**

현재 [predict.py](predict.py)에 미래 예보를 추가로 전달해도 실제 예보 모델로 바뀌지 않는다. `weather_strategy="forecast"`는 현재 전처리에서 거절된다. 기존 체크포인트의 decoder에 예보값을 바로 끼워 넣은 결과를 검증된 서비스 성능으로 제시하면 안 된다. 기존 CPU 샘플 재현과 날씨 포함/제거 비교의 근거는 [README.md](README.md), [evaluation.md](evaluation.md), [ablation/README.md](ablation/README.md)에 있다.

아래 내용은 **새로운 예보 지원 모델을 만들기 위한 데이터·학습·평가 규격 제안**이다. 현재 코드에 구현된 요청 형식이나 완료된 검증으로 읽지 않는다. 발주량, 재고, 비용, 안전재고 계산은 범위에 포함하지 않는다.

## 필요한 예보 기록과 예시 입력

예보 대상 날짜만 있는 표로는 당시 예측을 재현할 수 없다. 같은 날짜의 예보라도 발급 시각과 수정 버전에 따라 값이 달라지므로, 다음 필드를 원본과 함께 보관한다.

| 필드 | 의미·단위 | 예시 |
| --- | --- | --- |
| `as_of` | 마지막 확정 판매 이력의 현지 날짜, YYYY-MM-DD | `2026-10-23` |
| `as_of_at` | 모델이 정보를 사용할 수 있는 판단 시각, UTC 오프셋 포함 ISO 8601 | `2026-10-24T00:00:00+09:00` |
| `timezone` | 매장 판매일과 예보 집계일을 정의하는 IANA 시간대 | `Asia/Seoul` |
| `provider` | 예보 제공자 식별자 | `example-provider` |
| `station_id` | 제공자 네임스페이스 내 관측소 또는 예보 지점 ID | `example-station-001` |
| `mapping_version` | 검증된 매장↔예보 지점 대응표 버전 | `proposed-mapping-v1` |
| `issued_at` | 해당 예보 버전이 발급된 시각, UTC 오프셋 포함 | `2026-10-23T18:00:00+09:00` |
| `available_at` | 해당 버전을 당시 실제로 조회할 수 있었음이 확인되는 최초 시각 | `2026-10-23T18:10:00+09:00` |
| `revision_id` | 같은 발급 시각의 수정판을 구분하는 원본 버전 | `example-revision-1` |
| `target_date` | 예보가 설명하는 현지 날짜 | `2026-10-24` |
| `valid_from` / `valid_to` | 일별 값의 집계 구간, 시작 포함·끝 제외 | `2026-10-24T00:00:00+09:00` / 다음 날 00시 |
| `tavg`, `tmax`, `tmin` | 대상일 평균·최고·최저 기온, °C | `16.0`, `22.0`, `11.0` |
| `preciptotal` | 대상일 누적 강수량, mm/day | `5.0` |
| `avgspeed` | 대상일 평균 풍속, m/s | `2.5` |
| `units` | 필드별 명시적 단위 | 아래 JSON 참조 |
| `aggregation_version` | 시간별 예보를 일별 특징으로 만드는 정의·코드 버전 | `daily-local-v1` |

아래 JSON은 판매 이력과 상품 목록을 생략한 **부분 규격 예시**다. 시각·예보값·ID는 설명용이며 실제 수집 자료가 아니다. 예시 한국 시간대나 지점 ID를 기존 Walmart 매장·상품·관측소에 연결하지 않는다. 현재 `predict()`에 전달해 실행하는 샘플도 아니다.

```json
{
  "as_of": "2026-10-23",
  "as_of_at": "2026-10-24T00:00:00+09:00",
  "timezone": "Asia/Seoul",
  "dates": [
    "2026-10-24", "2026-10-25", "2026-10-26", "2026-10-27",
    "2026-10-28", "2026-10-29", "2026-10-30"
  ],
  "model_input": {
    "weather_strategy": "issued_forecast",
    "provider": "example-provider",
    "station_id": "example-station-001",
    "mapping_version": "proposed-mapping-v1",
    "aggregation_version": "daily-local-v1",
    "units": {
      "tavg": "degC", "tmax": "degC", "tmin": "degC",
      "preciptotal": "mm/day", "avgspeed": "m/s"
    },
    "forecast_weather": [
      {
        "issued_at": "2026-10-23T18:00:00+09:00",
        "available_at": "2026-10-23T18:10:00+09:00",
        "revision_id": "example-revision-1",
        "target_date": "2026-10-24",
        "valid_from": "2026-10-24T00:00:00+09:00",
        "valid_to": "2026-10-25T00:00:00+09:00",
        "tavg": 16.0,
        "tmax": 22.0,
        "tmin": 11.0,
        "preciptotal": 5.0,
        "avgspeed": 2.5
      }
    ]
  }
}
```

위 예시의 `forecast_weather`는 하루만 보여준다. 실제 7일 요청에는 선택한 예보 버전의 대상일별 기록을 중복 없이 7행 준비한다.

`available_at`은 나중에 아카이브를 내려받은 현재 시각과 구분한다. 과거 공개 시각이 확인되지 않고 발급 시각만 있는 자료는 주 평가에서 당시 이용 가능했던 예보로 취급하지 않는다. 공개 지연을 가정한 별도 실험은 그 가정과 미검증 상태를 명시한다.

## 예측 기준시각에 맞춘 결합

1. 매장 현지 판매일, 판단 시각 `as_of_at`, 관측소/예보 지점 대응을 먼저 확정한다. 기준일까지의 판매와 관측 날씨도 해당 시각까지 이용 가능했던 기록만 허용한다. 사후 정정 판매·기상 관측의 공개 시각을 알 수 없다면 그 한계를 별도로 기록한다.
2. 시간 비교는 UTC로 정규화하고 날짜 집계는 지정한 현지 시간대로 수행한다. 시간대 오프셋이 없는 시각, 중복 버전, 서로 모순되는 발급/가용 시각을 조용히 추정하지 않는다.
3. 해당 지점의 예보 중 `issued_at <= as_of_at`와 `available_at <= as_of_at`를 모두 만족하는 버전만 후보로 삼는다. 수정판도 자체 `available_at`을 적용한다. 현재 조회되는 최신 예보를 과거 기준일에 붙이지 않는다.
4. 사전에 정한 규칙으로 버전을 고른다. 첫 구현의 권장 규칙은 **당시 가용했고 요청 7일을 포함하는 가장 최근 발급 회차**이며, 동일 회차 수정판은 그때 가용한 최신판을 고른다. 날짜별로 다른 발급 회차를 섞는 정책을 택한다면 학습·평가·서버에서 같은 규칙을 사용하고 버전으로 남긴다.
5. 선택된 버전의 `target_date`와 예측 대상 날짜를 결합한다. `(store_id, product_id, as_of_at, target_date)`와 선택한 예보 ID를 함께 보존한다. 같은 대상 날짜도 기준일이 다르면 입력 예보가 달라질 수 있다.
6. 예보가 없거나 7일을 충족하지 못한 경우, 정한 결측/거절 정책을 적용하고 사유를 반환한다. 미래 실측값으로 메우지 않는다. persistence 대체를 허용하려면 명시적인 대체 모드로 학습·평가하고 응답에도 구분해야 한다.

매장↔지점 대응표에는 제공자, 지점 좌표, 적용 기간, 시간대, 선정 근거와 버전을 기록한다. 한국 매장/상품을 기존 Walmart ID에 임의 배정하지 않는다. 새 매장·상품의 판매 이력과 실질적인 기상 대응을 확보한 뒤 새 모델의 학습 대상과 범주로 등록한다.

## 전처리와 모델 변경

현재 모델은 encoder의 과거 관측과 decoder의 persistence 조건을 함께 학습했다. 실제 예보 지원에는 **각 학습 기준시점에 발급돼 있던 예보를 decoder에 넣는 별도 학습**이 필요하다. 미래 실측 날씨로 학습한 뒤 서버에서 예보로 바꾸는 방식도 동일 조건 학습이 아니다.

현재 단일 날짜 패널에 미래 날씨 열 하나를 추가하는 것만으로는 부족하다. 같은 대상 날짜에 대해 예측 기준시점마다 다른 예보가 존재하기 때문이다. 새 데이터셋은 기준시점·지점·대상일별 예보 조회표를 사용하거나, 각 window를 만들 때 해당 시점의 예보를 주입하는 방식으로 구성한다. 학습/검증/테스트/서버 모두 같은 선택 함수를 사용한다.

일별 집계 정의도 고정한다. `tavg`를 최고·최저의 평균으로 임의 대체하지 않는다. 시간별 자료를 집계하면 현지 날짜의 실제 길이와 유효시간을 반영하며, 강수의 누적·구간값 여부와 풍속 평균 정의를 기록한다. 공급자가 제공하지 않는 관측용 `precip_trace`를 실제로 관측한 0처럼 취급하지 않는다. 사용 가능한 예보 특징과 결측 지표를 정하고 새 모델에서 학습한다.

단위는 한 번 명시적으로 변환한다. 기존 Walmart 단위를 유지하는 설계라면 °C→°F는 `x * 9/5 + 32`, mm→inch는 `/25.4`, m/s→mph는 `/0.44704`다. SI로 새로 학습하는 설계도 가능하지만 해당 모델의 저장 단위와 전처리 버전을 함께 바꾼다. 다른 모델의 scaler나 중앙값을 재사용하지 않는다.

새 모델 묶음에는 체크포인트와 다음 항목을 함께 저장한다.

- 학습 구간에서만 fit한 encoder·scaler·target normalizer·결측 기본값.
- 관측/예보 특징 목록과 순서, 단위·일별 집계·결측 정책, 날짜 기준점과 `time_idx` 정의.
- 학습 대상 매장·상품·예보 지점 대응과 적용 기간, 범주 인코더.
- 예보 제공자·원본 버전·가용 시각 근거·선택 규칙, 입력 파일/아티팩트 해시.
- decoder 전략 `issued_forecast`, 모델 버전, 분할과 seed, 출력 분위수 순서, CPU 기준 샘플과 허용 오차.

기존 persistence 모델의 저장 전처리와 새 모델의 상태를 혼합하지 않는다. 배포 후 요청 중에는 새 통계를 fit하거나 재학습하지 않고 해당 버전의 저장 상태를 재사용한다.

## 누출을 막는 학습·검증·테스트

원본과 직접 비교하려면 기존 200개 시계열 및 다음 경계를 유지하고, 같은 상품·예측 기준일·대상일·실제 판매량을 비교해야 한다.

| 구간 | 대상 판매 날짜 |
| --- | --- |
| 학습 | 2012-01-01 ~ 2014-07-11 범위 안의 유효 window |
| 검증 | 2014-07-12 ~ 2014-09-05 |
| 테스트 | 2014-09-06 ~ 2014-10-31 |

각 window의 decoder 7일 전체가 한 구간 안에 들어가도록 한다. 경계를 가로질러 학습 label과 검증/테스트 label이 겹치는 window는 제외한다. 전체 window를 만든 뒤 무작위로 train/validation/test에 나누지 않는다. 검증/테스트는 원본처럼 7일 간격의 기준일을 사용해 같은 상품·대상 날짜의 중복 집계를 피한다.

encoder는 기준시점 이전 56일을 사용하므로 앞선 구간의 실제 이력이 포함될 수 있다. 뒤쪽 테스트 주차에서 그때까지 확정된 앞쪽 주차 판매를 사용하는 rolling-origin 평가도 가능하다. 이 경우에도 모델·전처리·예보 선택 정책을 테스트 구간에서 다시 fit하거나 조정하지 않는다. 검증 구간만으로 체크포인트와 정책을 결정하고 테스트는 마지막에 한 번 비교한다.

예보 자료가 있는 window만 따로 고르면 표본이 바뀐다. 그러므로 모델별 제외 사유와 가용률을 기록하고 **비교 모델 모두에 동일한 공통 window 집합**을 적용한다. 전체 원본 7,973행 및 현재 서버 정책에 맞는 최근 56일 전부 실제 관측 집합 1,701행과, 예보 가용 조건까지 적용한 새 집합을 혼용하지 않는다. 새 집합의 키 해시·기간·상품 수·행 수를 별도로 보존한다.

현재 2012~2014년 자료와 연결되는 실제 발급 예보 아카이브는 확보·검증하지 않았다. 해당 예보가 없으면 최근 날짜의 예보를 과거 날짜에 붙일 수 없다. 다른 기간이나 새 한국 매장 자료로 실험할 때는 모든 비교 모델에 동일한 새 시간 분할·상품·평가 행을 적용하고, persistence TFT와 날씨 제거 TFT도 해당 학습 구간에서 다시 학습한다. 기존 모델의 과거 테스트 지표를 새 기간의 실제 예보 모델과 직접 비교해 개선율을 주장하지 않는다.

## 공통 비교 기준과 출력 해석

비교 대상은 현재 방식의 persistence TFT, 날씨 제거 TFT, 현재 API 요일 기준선, 새 실제 예보 TFT다. 동일한 시간 분할과 평가 행을 사용하고, 가능한 경우 TFT 비교에는 같은 장비·런타임·학습 조건을 적용한다. 여러 seed를 반복하면 단일 학습 실행의 변동도 함께 보고한다. 현재 완료된 persistence/날씨 제거 비교의 장비·Python 차이는 [evaluation.md](evaluation.md)에 남아 있다.

| 지표 | 동일 행에서의 계산 |
| --- | --- |
| MAE | `mean(abs(actual - p50))` |
| WAPE | `sum(abs(actual - p50)) / sum(actual)`; 정답 합이 0이면 미정의로 표시 |
| 공통 3분위수 pinball | q=0.1/0.5/0.9 각각 `max(q*(actual-pq), (q-1)*(actual-pq))`를 계산한 뒤 모든 행·3분위수 평균 |
| P10~P90 포함률 | `mean(p10 <= actual <= p90)` |

API는 세 분위수만 제공하므로 공통 표에서 5분위수 평균 pinball과 섞지 않는다. 포함률과 함께 평균 구간 폭, horizon별·상품별 표본 수와 오차를 보고 넓은 구간만으로 높은 포함률을 얻는지 확인한다. 예보 제공 시점별 가용률과 결측/대체 비율도 성능표와 함께 제공한다.

`p10`, `p50`, `p90`는 **그 상품의 해당 날짜 판매 개수**에 대한 예측 분위수다. 7일 합계, 매출액, 발주량이 아니다. P50은 중앙값이며 평균과 같다고 가정하지 않는다. P10~P90은 명목상 중앙 80% 예측 구간이며, 평균 추정치의 신뢰구간이 아니다. 실제 포함률이 80%임을 보장하지 않으며, 각 날짜의 구간이 7일 전체를 동시에 80% 확률로 덮는다는 뜻도 아니다. 정수 판매의 동률과 0 판매를 고려해 실제 보정을 평가한다.

분위수는 소수 값을 가질 수 있는 연속 예측이다. 판매량에 임의 상한을 두거나 정수로 강제 반올림하지 않는다. 값의 상한과는 별개로 **현재 모델의 예측 길이는 7일**이며 요청 상품 수·응답 크기 등 API 제약은 API 규격을 따른다. 기존 출력 계약을 유지한다면 5분위수 `[0.10, 0.25, 0.50, 0.75, 0.90]`의 0·2·4번째를 사용하고, 유한값 검사 후 0 미만 절단·5개 분위수 정렬을 적용한다. 원시 출력과 후처리 성능을 모두 남긴다.

현재 완료된 것은 historical persistence CPU 재현, 동일 행의 기준선 비교, 실제 날씨 제거 학습이다. **실제 발급 예보 수집, 당시 가용 시각 검증, 예보 decoder 재학습, 실제 예보 성능과 운영 데이터 성능은 아직 미검증**이다. 이 항목을 충족하고 새 버전의 CPU 샘플 재현을 통과한 뒤 실제 예보 지원을 활성화한다.
