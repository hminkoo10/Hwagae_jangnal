# 심사 질문과 근거 있는 답변

답변은 **기존 Walmart TFT**의 과거 평가와 CPU 재현 범위를 기준으로 한다. 동일 환경 3개 seed 쌍 비교도 Walmart 자료를 대상으로 하며 진행 중이다. 서버 연결·Ubuntu 검증은 팀원 측 완료 사항으로 전달받았으며 이 문서에서 재검증하거나 성능을 대신 주장하지 않는다.

main의 [일반 매장용 `merchant_tft`](../merchant_tft/README.md)는 합성 자료로 학습한 별도 TFT이며 실제 예보 입력을 받는다. **Walmart의 6.98%·10.71%나 이번 3개 seed 실험 결과는 그 모델의 정확도가 아니다.** 합성 모델의 실매장 성능·실제 예보 효과는 미검증이며 해당 작업은 이번 PR 범위 밖이다.

## 1. 왜 TFT를 선택했나요? 더 단순한 모델보다 낫나요?

**답변:** 매장·상품 같은 고정 정보, 과거 판매·날씨, 미래에 알 수 있는 달력을 함께 사용해 다음 7일의 분위수를 예측하는 입력 구조와 맞아서 선택했습니다. 실제로 현재 API의 요일 기준선보다 테스트 MAE가 낮았습니다. 하지만 XGBoost·LSTM 등 모든 후보를 같은 조건에서 비교한 것은 아니므로 “가장 좋은 모델”이라고 주장하지 않습니다.

TFT 구조의 적합성은 [원 논문](https://arxiv.org/abs/1912.09363), 우리 모델의 설정은 [학습 노트북](../notebooks/startup_thon_1.ipynb), 직접 비교한 범위는 [평가표](../evaluation/api-comparison/metrics.csv)를 근거로 구분합니다. attention이 있다는 이유만으로 예측 원인이 설명되었다고도 말하지 않습니다.

## 2. “6.98% 개선”은 무엇과 비교한 숫자인가요?

**답변:** 기존 Walmart TFT를 저장소 API의 실제 요일 기준선과 같은 7,973개 상품·일 예측에서 비교한 **P50 MAE의 상대 감소율**입니다. MAE가 5.9363에서 5.5221로 줄었습니다. 기준선은 기준일까지 최근 84일의 같은 요일 관측으로 P10/P50/P90을 계산하며, 요일마다 최소 4일의 관측이 필요합니다.

이는 정확도가 6.98%p 늘었다는 뜻이 아닙니다. 선택된 200개 매장·상품 조합, 2014-09-06~10-31 테스트의 결과입니다. 26.99%라는 별도 숫자는 원본의 seasonal naive+검증 잔차 보정 기준선 대비 결과이므로 현재 API 대비 개선율로 사용하지 않습니다. [실제 API 함수](../../apps/api/app/forecasting.py), [재계산 코드](../evaluate.py), [평가 설명](../evaluation.md)

## 3. 10.71%가 더 좋은데 왜 그 숫자만 보여주지 않나요?

**답변:** 10.71%는 최근 56일의 판매가 하루도 빠지지 않은 **55개 조합·243개 창·1,701행**에 한정됩니다. 기존 Walmart `ml.predict.predict()`의 입력 조건을 만족하는 부분집합이라 별도로 보고했습니다. 전체 200개 조합·1,139개 창·7,973행의 결과는 6.98%이며, 두 모집단이 다릅니다.

과거 학습/평가의 encoder에는 판매 누락이 있는 창도 있었지만 현재 전달 함수는 이력 부족 시 숫자를 만들지 않습니다. 이 차이를 숨기지 않기 위해 두 표를 모두 제시했습니다. [행 집합 manifest](../evaluation/api-comparison/manifest.json), [전처리의 이력 검사](../preprocess.py)

## 4. API는 84일이고 TFT는 56일이면 공정한 비교인가요?

**답변:** 기존 API 동작을 유지한 대체 후보 비교입니다. 예측 기준일·상품·대상 날짜·정답은 같지만 입력 길이는 같지 않습니다. 따라서 확인된 것은 이 설정의 두 예측 경로 간 차이이며, TFT 구조만의 우월성은 아닙니다. 56일이 최적이라는 이력 길이 탐색 결과도 없습니다.

대표 사례 그림에서는 전달된 56일 판매로 기준선을 계산합니다. 그 사례 수치를 전체 84일 기준선 평가와 합치지 않습니다. [전체 평가](../evaluation.md), [대표 사례와 기준선 범위](cases.md)

## 5. 날씨를 넣어서 실제로 좋아졌다는 증거가 있나요?

**답변:** 기존 Walmart 단일 실행에서는 날씨를 포함한 모델이 날씨 제거 모델보다 전체 MAE 2.91%, 56일 부분집합 MAE 5.88% 낮았습니다. 다만 GPU와 Python 환경이 달라 순수한 날씨 효과라고 단정할 수 없습니다. 이를 보완하기 위한 Walmart 자료의 같은 환경 seed 42·43·44 포함/제거 쌍 비교가 진행 중이며 아직 최종 수치를 주장하지 않습니다.

날씨 제거 실험은 기온·강수·풍속 관련 값과 결측/trace 표시를 제거하고 관측소 식별자·달력을 남겼습니다. 같은 키와 실제 판매량을 비교했지만 무작위 실험에 의한 인과 효과를 측정한 것은 아닙니다. seed 42의 기존 결과를 확인한 뒤 반복 실험 계획을 세웠으며, 3개 seed만으로 유의성을 단정하지 않습니다. [단일 실행 근거](../ablation/completed-run.json), [행 정렬 검증](../evaluate.py)

## 6. 미래 날씨는 실제 예보인가요, 나중에 알게 된 실측인가요?

**답변:** 기존 Walmart 모델은 기준일까지의 과거 관측 날씨를 사용하고 마지막 특징값을 미래 7일에 유지하는 persistence입니다. 원본 collator가 미래 구간의 날씨를 이렇게 덮어씁니다. 이 모델을 실제 발급 예보로 학습·평가한 모델이라고 소개하지 않습니다.

Walmart 함수에 미래 예보값을 추가로 보내는 것만으로 예보 모델이 되지 않습니다. 발급·가용 시각이 남은 과거 예보를 확보하고, 기준시각에 볼 수 있었던 버전만 사용하도록 전처리와 새 모델을 학습·검증해야 합니다. 별도 [합성 학습 `merchant_tft`](../merchant_tft/README.md)는 실제 예보 입력을 받지만, 실매장 정확도와 예보의 실세계 예측 기여는 아직 검증하지 않았습니다. [원본 노트북 cell 10·13](../notebooks/startup_thon_1.ipynb), [Walmart 모델의 예보 지원 계획](../forecast-support.md)

## 7. P10, P50, P90은 각각 무엇인가요? 80% 신뢰구간인가요?

**답변:** 같은 입력 조건에서 판매량 분포의 10·50·90% 위치를 추정한 분위수입니다. P50은 중앙값이고 P10~P90은 목표상 중앙 80% 예측 구간입니다. 모수의 80% 신뢰구간이나 매번 80% 확률을 보증하는 숫자로 설명하지 않습니다.

전체 테스트에서 실제 판매가 구간 안에 들어온 비율은 84.59%입니다. 그러나 실제 판매 0이 47.15%이고 동률·0 하한·정렬의 영향이 큽니다. `실제 판매 ≤ P10` 비율은 52.49%여서 개별 분위수가 명목 비율대로 보정됐다고 말할 수 없습니다. 구간 포함률뿐 아니라 폭과 pinball 손실도 같이 보고합니다. [분위수·포함률 근거](../evaluation.md)

## 8. 다섯 분위수인데 웹에는 왜 세 개만 반환하나요?

**답변:** 학습 출력은 P10/P25/P50/P75/P90 다섯 개이고 현재 API 계약은 P10/P50/P90 세 개입니다. 원본과 같은 방식으로 음수를 0으로 제한하고 다섯 값을 정렬한 뒤 인덱스 0·2·4를 선택합니다. 날짜와 상품 순서는 요청대로 보존합니다.

정렬은 역전을 없애는 후처리이고 원시 P50이 바뀔 수도 있습니다. 원시 모델의 품질을 숨기지 않도록 평가에는 원시·후처리 지표를 구분했습니다. 원본 테스트 원시 출력은 36.45%의 행에서 분위수 역전이 있었고 NaN/Inf는 없었습니다. 실행 중 비유한값이 나오면 임의 숫자로 교체하지 않고 오류 처리합니다. [추론 후처리](../predict.py), [원시·후처리 비교](../evaluation.md)

## 9. 판매가 0인 날과 판매 기록이 없는 날은 어떻게 구분하나요?

**답변:** 관측된 0은 유효한 판매 기록입니다. 기록 누락·null·미확정 판매를 0으로 채우지 않습니다. 기존 Walmart 함수는 상품별로 연속 56일 중 하루라도 관측이 없으면 `insufficient_history`와 사유, 빈 예측을 반환하고 같은 요청의 정상 상품은 계속 예측합니다.

여기서 관측 판매 0은 잠재 수요가 반드시 0이라는 뜻도 아닙니다. 재고·품절·프로모션 이력이 없어 실제 수요 부재와 판매 기회 제한을 분리하지 못합니다. 품절로 못 판 수요를 별도로 복원한 모델이 아니며, 예측 목표는 데이터에 기록된 판매 개수입니다. 재고 제한이 없는 잠재 수요를 추정한다고 보장하지 않습니다. [이력 검사](../preprocess.py), [이력 부족 실제 샘플](../examples/insufficient-history.json), [0판매 사례](cases.md)

대표 0판매 사례인 매장 4·상품 93은 과거 56일과 다음 7일의 실측이 모두 0이고 두 모델의 P50 MAE도 0입니다. 이때 WAPE는 실제 판매 합계가 0이라 정의되지 않으므로 0%라고 만들지 않고 `null`로 표시합니다.

## 10. 미래 정보가 학습이나 예측에 섞인 것은 아닌가요?

**답변:** 무작위 분할 대신 학습 2012-01-01~2014-07-11, 검증 07-12~09-05, 테스트 09-06~10-31로 나눴습니다. 시계열 선택과 날씨 중앙값은 학습 구간에서 정했고 전처리는 과거 방향으로 채웁니다. API 기준선도 각 기준일까지의 84일만 받고, 기존 Walmart 추론 입력의 기준일 이후 판매·날씨 관측은 거절합니다.

테스트는 매주 기준일을 옮기는 rolling-origin 평가입니다. 다음 주에는 그때까지 관측된 이전 테스트 주의 판매를 사용할 수 있지만 모델을 다시 학습하지 않습니다. 한 기준일에서 56일 전체를 한 번에 맞힌 평가가 아닙니다. 또한 원본에는 실제 데이터 공개 시각이 없어 시각 단위 가용성까지 검증하지는 못했습니다. “모든 종류의 누출이 완전히 배제됐다”는 포괄적 보증 대신 확인한 경계를 설명합니다. [시간순 평가](../evaluation.md), [미래 입력 거절 테스트](../tests/test_preprocess.py), [기준선 누출 검사](../tests/test_evaluate.py)

## 11. 실패하는 경우도 보여줄 수 있나요?

**답변:** 정상·변동·0판매 대표 사례와 별도로, 테스트에서 오차가 큰 창을 찾아 공개합니다. 대표 사례는 예측 전 56일 통계로 선정했고, 실패 사례는 결과를 보고 선정한 진단입니다. 평균 개선이 모든 상품·모든 주의 개선을 뜻하지 않는다는 점을 보여줍니다.

예를 들어 매장 17·상품 9의 2014-09-12 기준 다음 7일에서 TFT MAE는 **73.354**, 84일 API 기준선은 **52.071**로 TFT가 더 나빴습니다. 최근 56일 실측이 모두 있는 243개 창 중 큰 오차를 사후 선정한 사례이므로 전체 평균을 대표하지는 않습니다.

해당 창의 급격한 수요 변화나 구간 이탈은 관측할 수 있지만, 원본에 없는 행사·품절·가격 변화 등을 실제 원인으로 만들어 설명하지 않습니다. 예측 실패의 원인 추정과 측정된 오차를 구분합니다. [대표 사례](cases.md), [실패 사례](failure-cases.md)

## 12. 신규 상품이나 한국 매장에도 바로 적용할 수 있나요?

**답변:** 기존 Walmart 모델은 저장된 200개 매장·상품 조합과 관측소 대응을 검사합니다. 새 그룹이나 명시적 상품 매핑이 없는 요청에는 예측을 만들지 않습니다. 한국 상품에 임의 Walmart 번호를 붙이는 방식도 지원하지 않습니다.

Walmart 모델에 새 매장·상품을 등록하려면 실제 판매 이력과 기상 지점 대응을 확보하고, 별도 오프라인 학습·평가 후 새 모델과 저장 전처리를 등록해야 합니다. 56일 이력만 있다는 이유로 이 모델의 미등록 그룹을 지원하는 것은 아닙니다. 별도 `merchant_tft`는 매장·상품 ID를 Walmart 범주에 매핑하지 않는 합성 학습 모델이며 실매장 성능은 미검증입니다. [대응표](../metadata/selected_series.csv), [신규 그룹 처리](../preprocess.py), [합성 모델의 입력·한계](../merchant_tft/README.md)

## 13. 실시간으로 매 요청마다 다시 학습하나요? CPU로 가능한가요?

**답변:** 기존 Walmart 함수는 요청 중 재학습하지 않습니다. 체크포인트와 학습된 전처리를 프로세스에서 재사용해 CPU로 추론합니다. 입력은 하루 단위 판매이며 기준일은 마지막 확정 판매일입니다. 실시간 거래 스트림을 즉시 학습하는 시스템이라고 설명하지 않습니다.

로컬 Windows CPU thread 1에서 10개 조합을 3개 매장 요청으로 순차 처리했을 때 import 포함 첫 실행 8.34초, 재사용 반복 중앙값 0.21초였습니다. 50개 조합·10개 매장 요청은 10.24초/0.96초였습니다. API 네트워크·동시 사용자 부하를 포함한 목표 서버 응답시간 보장이 아닙니다. 서버 연결/Ubuntu 검증은 팀원 담당 완료 사항으로 전달받았습니다. [CPU 실행 방법·한계](../README.md), [10상품 측정](../evaluation/benchmarks/windows-10.json), [50시계열 측정](../evaluation/benchmarks/windows-50.json)

## 14. 발표 성능 수치는 CPU에서 전체 데이터를 다시 돌린 결과인가요?

**답변:** 기존 날씨 TFT의 전체 성능은 저장된 GPU 테스트 예측 CSV를 같은 정답으로 다시 집계한 결과입니다. CPU에서는 실제 10상품×7일×5분위수 샘플을 재현하고 별도의 CPU 기대값과 비교했습니다. 전체 날씨 TFT 테스트를 CPU로 다시 추론한 평가와 구분합니다.

CPU 샘플 비교 허용 오차는 절대 `1e-4`, 상대 `1e-5`입니다. 초기 두 상품의 GPU와 CPU 값에는 최대 약 0.0235 차이가 있어 GPU CSV를 이 작은 오차의 CPU 기준값으로 사용하지 않습니다. 평가표 재집계 비교의 `1e-12` 허용 오차는 또 다른 검증입니다. [CPU 재현](../README.md), [평가 재생성](../evaluation.md)

## 15. 그러면 P90만큼 발주하면 되나요?

**답변:** 이 함수는 일별 판매량 예측을 반환합니다. 발주량은 현재고·입고 예정·납기·최소 발주 단위·폐기 비용 같은 조건을 추가로 반영해야 하며 기존 API가 담당합니다. P90을 곧바로 자동 발주량으로 정의하지 않습니다.

원본 재고 자료는 `DEMO_NOT_FOR_ORDERING`으로 표시되어 있습니다. 이 평가로 재고 절감·폐기 감소·품절률 개선이나 실제 발주 정책의 효과를 검증했다고 주장할 수 없습니다. [범위와 데이터 한계](../evaluation.md), [실행 설정](../evaluation/run_config.json)

## 16. 결과를 직접 재현해볼 수 있나요?

**답변:** 저장소에 평가 입력 ZIP과 해시, 재계산 코드, 기준표가 있습니다. 체크포인트 없이 저장 예측의 평가표를 다시 만들 수 있고, CPU 추론 재현에는 전달된 동일 체크포인트가 필요합니다.

저장소 루트에서 실행합니다.

```bash
python -m zipfile -e ml/evaluation/tft-evaluation-data.zip data/runtime/tft-evaluation
python data/runtime/tft-evaluation/evaluation-data/reproduce.py
```

입력 SHA-256을 확인한 뒤 세 모델×두 집합의 6행을 만들고, 행 키·건수 및 지표를 기존 표와 비교합니다. 지표의 절대·상대 허용 오차는 각각 `1e-12`이며 불일치하면 실패합니다. 이 ZIP은 기존 Walmart 단일 실행 비교를 재현하며 **진행 중인 동일 환경 3개 seed 실험이나 별도 `merchant_tft`의 결과를 포함하지 않습니다**. [ZIP 식별 정보](../evaluation/external-data.json), [평가 실행 코드](../evaluate.py)

## 17. 7일의 P50을 더하면 주간 판매량의 중앙값인가요?

**답변:** 아닙니다. 각 날짜의 중앙값을 합한 값이 전체 합계의 중앙값과 같다는 일반적인 보장은 없습니다. 현재 결과를 합산해 보여준다면 ‘일별 P50 합계’라고 표시하고 주간 중앙값이라고 부르지 않습니다. 일별 P10/P90을 더한 범위도 주간 80% 예측 구간이라고 설명하지 않습니다.

주간 총량의 분위수를 제공하려면 날짜 간 변동이 함께 움직이는 관계까지 반영한 별도 추정과 평가가 필요합니다. 현재 [출력 계약](../README.md)은 날짜별 분위수이며 그러한 주간 분포를 검증하지 않았습니다.
