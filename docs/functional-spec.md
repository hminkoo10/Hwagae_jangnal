# 화개장날 기능 명세서

- 상태: **v0.3 — 요구사항 인터뷰 진행 중, 웹·API 초기 구현 추가**
- 기준일: 2026-10-24, Asia/Seoul
- 팀: 화개장터
- 작업명: 화개장날. 최종 이름은 미확정.

이 문서는 앞으로 만들 서비스의 명세입니다. 현재 구현 상태와 구분합니다.
사용자가 구현을 요청해 초기 뼈대를 추가했습니다. [구현 현황](implementation.md)의 정책은 수정 가능한 초기 선택이며, 인터뷰 답변으로 확정한 요구와 구분합니다.
`요구 확정`은 사용자가 요청한 기능이며, `설계 제안`은 구현 방법의 제안입니다.
`답변 대기` 항목은 승인된 것으로 간주하지 않습니다.
원문 답변과 남은 질문은 [요구사항 인터뷰 기록](requirements-interview.md)에 정리합니다.

## 1. 제품과 범위

**완제품 식품을 받아 파는 점주가, 앞으로 7일의 상품별 판매 수량을 예측하고 재고를 입력한 뒤 추가 발주 개수를 결정하는 웹앱입니다.**

| 항목 | 확정 내용 |
| --- | --- |
| 문제 | 날씨에 따른 판매 변동으로 발생하는 폐기와 품절 손실의 균형 |
| 첫 업종 | 완제품을 매입해 판매하는 식품 매장. 수량 단위는 상품별 개수 |
| 첫 사용자 | 심사위원이 샘플 매장으로 기능 체험 |
| 지원 규모 | 여러 매장, 매장당 10~50개 상품. 시연에 넣을 정확한 개수는 미정 |
| 판매 기록 | CSV·Excel·직접 입력 모두 지원 |
| 재고 미입력 | **수요 예측만 표시. 발주량은 계산하지 않음** |
| 납기·판매 가능 기간 | 공급사마다 납기가 다르고, 상품마다 판매 가능 기간이 다름 |
| 예측 기간 | 앞으로 7일 |
| 날씨 | 실시간 예보와 과거 날짜 재생 모두 지원 |
| 비용 입력 | 판매가와 개당 매입 원가 |
| 계정 | 점주·직원 계정, 여러 매장 관리 |
| 발주 결과 | 수량 수정·저장·발주서 파일 내보내기 |
| 선택 희망 | 글을 AI가 판매 기록으로 정리하는 입력 기능. 구체적인 방식은 미정 |
| 형태 | PC·모바일에서 사용하는 반응형 웹. PWA 홈 화면 설치 제외 |
| 디자인 | 배민 사장님 사이트처럼 세련되고, 한눈에 파악하고 조작하기 쉬운 분위기 |
| 데이터 | 현재 공개 자료만 있음. 실제 점포 자료는 미확보 |
| 대회 | 디미고 스타트업 해커톤. 심사 기준·배점 미확인 |
| 마감 | 사용자 표현은 ‘3일 뒤’. 기준일로 계산하면 **2026-10-27**, 정확한 시각 확인 필요 |
| 팀 | 웹·API에 강한 개발자 1명, Colab·모델에 강한 개발자 1명. AI 코딩 보조 활용 |

업체 제휴나 운영자의 재고 확보 없이 체험할 수 있어야 합니다.
원재료·레시피 환산, 실제 공급사 자동 주문, 네이티브 앱은 현재 요청 범위에 포함하지 않습니다.
회원가입·직원 초대의 깊이, 알림, 날씨 변경 시나리오는 답변을 받은 뒤 확정합니다.

### 1.1 기능의 확정 수준

| 구분 | 기능 |
| --- | --- |
| 요구 확정 | 여러 매장과 역할별 계정, 상품별 설정, CSV·Excel·직접 입력, 7일 예측, 실시간 날씨·과거 재생, 재고 직접 입력 후 발주 계산, 수량 수정·저장·파일 내보내기 |
| 방식 결정 필요 | 계정 생성, 직원 권한, 재고 유통기한 관리, 납기 설정, 발주 주기, 파일 형식, 업로드 후 모델 갱신 |
| 선택 희망 | AI 텍스트 입력 |
| 포함 여부 미정 | 알림, 날씨 변경 시나리오, 사용자별 결과 비교의 상세 범위 |
| 제외 확정 | PWA 홈 화면 설치 |

3일 일정에 맞추기 위해 필수 기능을 임의로 제외하지 않습니다.
구현 깊이와 우선순위는 질문 23~32의 답변으로 결정합니다.

## 2. 핵심 사용자 흐름

1. 점주 또는 직원 계정으로 체험에 진입합니다. 계정 사전 생성·회원가입 방식은 미정입니다.
2. 접근 가능한 샘플 매장을 선택합니다.
3. 상품·판매 기록·지역·날씨 출처를 확인합니다.
4. 앞으로 7일의 상품별 예측과 예측 범위를 봅니다.
5. 재고 미입력 상품에는 `재고 입력 후 발주량 계산 가능`을 표시합니다.
6. 사용자가 재고를 직접 입력하고, 납기·판매 가능 기간·가격·원가를 확인합니다.
7. 계산 가능한 상품의 추천 발주량을 확인하고 필요하면 수정합니다.
8. 계획을 저장하고 발주서로 내보냅니다. 직원의 최종 확정 권한은 미정입니다.
9. 과거 날짜를 선택해 예측·실제 판매·비교 정책을 재생합니다.

**‘예상 40개 판매’와 ‘40개 추가 발주’는 다른 값입니다.**
재고가 미입력된 상품에 예측 수량을 발주량으로 대신 표시하지 않습니다.

## 3. 화면 구성 제안

| 화면 | 주요 내용 | 중요한 상태 |
| --- | --- | --- |
| 요약 | 매장 선택, 날짜, 날씨, 예측 가능한 상품 수, 재고 입력 필요 수 | 재고 미입력·예측 부족·발주 계산 가능 |
| 7일 예측 | 상품 검색, 일별 예측, 예측 범위, 날씨, 모델·자료 기준 | 판매 기록 부족·날씨 누락·과거 실험 |
| 발주 계획 | 추천량, 현재 재고, 입고 예정, 도착일, 수정 수량, 예상 매입액 | 계산 불가 사유·수정 후 재확인·저장 |
| 판매 기록 | CSV·Excel 업로드, 직접 입력, 미리보기, 오류 수정 | 가져오기 전·오류·중복·완료 |
| 재고 | 직접 입력, 재고 기준일시, 입고 예정, 유통기한 방식 | 미확인·확인된 0개·정보 오래됨 |
| 상품·공급사 | 상품 ID·이름·가격·원가·납기·판매 가능 기간 | 필수 설정 누락 |
| 과거 재생 | 기준 날짜, 당시 입력 자료, 예측과 실제 판매, 기준선 비교 | 관측 날씨 참고 실험·당시 예보 검증 |
| 매장·계정 | 접근 가능한 매장, 점주·직원 역할 | 권한 없음·매장 전환 |

화면 구성은 설계 제안입니다. 메뉴를 늘리기보다 서로 연관된 입력과 결과를 가까이 배치합니다.
PC에서는 표 중심으로 비교하고, 모바일에서는 상품별 카드 또는 가로 스크롤 표로 핵심 값을 유지합니다.
상단의 매장·날짜·모드가 바뀌면 모든 화면이 같은 기준을 사용해야 합니다.

디자인 제안: 밝은 바탕, 민트·초록 계열 강조색, 읽기 쉬운 큰 수량, 짧은 안내 문구.
추천량·입력 필요 상태·저장 버튼의 우선순위를 명확히 합니다. 참고 사이트의 상표나 화면 자산을 복제하지 않습니다.

## 4. 기능별 처리와 완료 조건

### F01. 계정·매장 접근 — 요구 확정, 권한 상세 미정

- 입력: 로그인 정보, 선택 매장, 계정과 매장의 소속 관계.
- 출력: 접근 가능한 매장 목록, 현재 역할, 선택 매장의 자료.
- 점주·직원 계정과 여러 매장을 지원합니다. 계정 사전 생성·가입·초대 방식은 질문 23에서 결정합니다.
- 서버가 매장 소속과 작업 권한을 검사합니다. 화면에서 버튼을 숨기는 것만으로 접근을 제한하지 않습니다.
- 완료 조건: 다른 매장 ID로 직접 요청해도 권한 밖의 판매·재고·발주 자료를 조회·수정할 수 없습니다.
- 답변 대기: 직원의 발주안 작성·최종 확정·내보내기 권한, 공개 체험의 진입 방식.

### F02. 상품·공급사 설정 — 요구 확정, 입력 구조는 제안

- 기본 입력: 매장, 상품 ID, 상품명, 판매 단위 `개`, 판매가, 개당 매입 원가.
- 추가 필수 설정: 입고 소요 기간, 상품의 판매 가능 기간. 공급사 기본값과 상품별 예외를 둘지는 질문 19에서 결정합니다.
- 서로 다른 상품을 이름이 비슷하다는 이유로 자동 병합하지 않습니다. 연결 기준은 상품 ID입니다.
- 금액은 유한한 0 이상 값, 기간·수량은 정해진 단위의 값만 허용합니다.
- 판매가가 원가 이하이면 입력을 조용히 변경하지 않고 비용 기반 발주 정책을 적용할 수 없는 사유를 안내합니다.
- 완료 조건: 판매·재고·예측·발주·내보내기에서 동일한 상품 ID와 단위를 사용합니다.
- 답변 대기: 공급사별 납기, 당일 도착 지원, 주문 마감·배송 요일, 주문 묶음·최소 주문량의 필요 여부.

### F03. 판매 기록 입력 — CSV·Excel·직접 입력 요구 확정

- 일별 집계 입력안: `매장`, `판매일`, `상품 ID`, `판매 개수`.
- 파일 형식 제안: `.csv`, `.xlsx`. 구형 `.xls`·여러 시트 처리 여부는 후속 확정합니다.
- 흐름: 파일 선택 → 열 연결 → 미리보기·검사 → 사용자 확인 → 저장 결과.
- 직접 입력도 같은 상품·날짜·수량 검사를 사용합니다.
- 잘못된 날짜·미등록 상품·빈 값·음수·소수 수량은 해당 행과 이유를 표시합니다. 반품·취소는 정책 확정 전 정상 판매에 섞지 않습니다.
- 같은 매장·상품·날짜의 기존 기록과 충돌하면 중복을 알려줍니다. 덮어쓰기·합산 정책 확정 전 자동 변경하지 않습니다.
- 누락 날짜는 0개 판매와 구분합니다. 휴무·품절·미수집을 임의로 같은 값으로 채우지 않습니다.
- 매출액만 있는 자료를 가격 가정으로 나누어 실제 판매 개수라고 저장하지 않습니다.
- 완료 조건: 저장 전 대상·행 수·오류를 확인할 수 있고, 저장 후 정상 반영 수와 실패 사유를 확인할 수 있습니다.
- 답변 대기: 업로드 후 새 매장 모델 학습 여부, 파일 크기·행 수 제한, 중복 처리, 데이터 수정·삭제 범위.

### F04. AI 글 입력 — 선택 희망, 방식 답변 대기

- 후보: ‘어제 우유 20개, 샌드위치 15개’ 같은 문장이나 복사한 표를 판매 기록으로 변환.
- 사진 OCR·웹페이지 수집과는 개발 범위가 다릅니다. 질문 25의 답변 전 어느 방식도 필수로 확정하지 않습니다.
- 설계 제안: 날짜·상품·수량을 추출한 뒤 미리보기에서 사용자가 확인하고 저장합니다.
- 추출하지 못한 값은 비워 두고 확인을 요청합니다. 원문에 없는 상품·날짜·수량을 추측해 확정하지 않습니다.
- 완료 조건 제안: 최종 저장 자료와 원문을 비교할 수 있고, 일반 입력과 같은 검사를 통과합니다.
- 답변 대기: 입력 종류, 확인 과정, 외부 AI 사용 서비스와 예산.

### F05. 재고·입고 예정 — 직접 입력 전 발주량 미표시 확정

- 입력안: 상품, 사용 가능한 현재 수량, 재고 확인 시각, 입고 예정 수량·도착일.
- 재고 미입력은 `null`에 해당하는 **미확인 상태**입니다. 사용자가 직접 입력한 `0개`와 다릅니다.
- 재고 미입력 상품은 수요 예측만 제공합니다. 발주량·발주 예상 비용을 계산하지 않으며, 값 자리에 `—`와 이유를 표시합니다.
- 일부 상품만 입력했다면 입력한 상품부터 계산합니다. 총액은 계산 가능한 상품만 포함한 부분 합계임을 표시합니다.
- 재고 입력만으로 모든 상품을 자동 계산하지 않습니다. 납기·판매 가능 기간·입고 예정 확인 등 나머지 조건도 충족해야 합니다.
- 입고 예정이 없다는 확인과 입고 예정 미확인을 구분합니다. 미확인 수량을 자동으로 0으로 빼지 않습니다.
- 저장된 발주안은 실제 입고 재고가 아닙니다. 실제 입고 또는 계산에 반영할 예정 입고의 상태를 구분합니다.
- 유통기한 지난 수량은 판매 가능 재고에서 제외합니다. 배치별 수량·만료일과 사용 순서의 상세 방식은 질문 18에서 결정합니다.
- 완료 조건: 재고 미입력 → 예측만 표시, 직접 0개 입력 → 다른 필수 조건 충족 시 발주 계산 가능. 두 상태가 혼동되지 않습니다.
- 답변 대기: 배치별 만료일, 재고 갱신 주기, 실사 수정, 재고 파일 가져오기 필요 여부.

### F06. 실시간 날씨·과거 재생 — 요구 확정

- 입력: 매장 위치, 기준 날짜, 날씨 모드.
- 출력: 예측 날짜의 기온·강수 등 사용 가능한 항목, 출처, 적용 지역, 발표·조회 시각.
- 실시간 모드는 현재 제공되는 예보를 사용합니다. 과거 모드는 당시 관측과 당시 이용 가능했던 예보를 구분합니다.
- 예보 통신 실패·일부 날짜 누락·기존 캐시를 쓰는 상태를 표시합니다. 실패를 맑음·0mm로 대체하지 않습니다.
- 날짜별 제공 변수·시간 해상도가 다르면 공통 변수로 변환하거나 누락을 표시합니다.
- 완료 조건: 현재 예보, 과거 관측 자료, 가정한 시나리오를 사용자가 구별할 수 있습니다.
- 답변 대기: 제공처, 서비스 계정·예산, 갱신 주기, 공개 과거 자료와 실시간 체험 연결 방식.

기상청 단기예보는 글피까지이므로 단독으로 7일 전체를 채울 수 없습니다.
기상청을 쓰면 중기예보 연계가 필요하며 제공 변수·공간 해상도 차이를 처리해야 합니다.
대안은 7일 이상을 제공하는 Open-Meteo입니다. 제공처는 아직 확정하지 않았습니다.
출처: [기상청 단기예보](https://www.data.go.kr/data/15084084/openapi.do),
[기상청 중기예보](https://www.data.go.kr/data/15059468/openapi.do),
[Open-Meteo Forecast API](https://open-meteo.com/en/docs).

### F07. 상품별 7일 예측 — 요구 확정, 모델 선택 위임

- 입력: 발주 판단 시점까지 확보된 판매 이력, 예보, 달력 정보, 상품·매장 식별자.
- 기간 제안: 매장 현지 시각의 영업 마감 후를 기준으로 **다음 날부터 7일, D+1~D+7**. 정확한 기준 시각은 미정입니다.
- 출력 제안: 상품·날짜별 P10·P50·P90, 생성 시각, 판매 자료 마감일, 모델 버전, 날씨 자료 기준.
- P50은 중앙값이며 ‘평균 판매량’으로 바꾸어 부르지 않습니다. P90을 ‘정확도 90%’라고 표시하지 않습니다.
- 예측값은 음수가 아니어야 하고, 하위 분위수 ≤ 중앙값 ≤ 상위 분위수 관계를 확인합니다.
- 공개 판매량으로 학습하면 관측된 판매량을 예측하는 것입니다. 품절로 놓친 수요를 모두 복원했다고 주장하지 않습니다.
- 새 매장·새 상품·이력 부족·날씨 누락에 대해 모델 사용 가능 여부를 표시합니다. 지원하지 않는 자료에 임의의 예측을 반환하지 않습니다.
- 완료 조건: 상품별 7개 날짜가 명확하고, 계산 불가 날짜는 사유가 있으며, 학습과 서버 추론이 같은 전처리를 사용합니다.
- 답변 대기: 최소 이력 길이, 신규 입력의 학습 방식, 최종 분위수·기준 시각.

모델 개발 순서는 **요일 기준선 → LightGBM 분위수 회귀 → 필요하면 TFT 비교**로 정합니다.
이는 3일 일정에서 비교 가능한 기준선을 먼저 확보하기 위한 설계 선택이며, LightGBM이 항상 더 정확하다는 뜻은 아닙니다.
최종 모델은 동일한 시간 분할에서 검증한 결과로 선택합니다. TFT 사용은 필수가 아닙니다.
LightGBM은 분위수 회귀 목표와 분위수 수준 설정을 지원합니다.
출처: [LightGBM 공식 파라미터 문서](https://lightgbm.readthedocs.io/en/stable/Parameters.html).

### F08. 추가 발주량 계산 — 요구 확정, 세부 정책 미정

- 입력: 예측, 사용 가능 재고, 입고 예정, 납기, 발주 주기, 판매 가능 기간, 가격·원가.
- 출력: 추천 추가 발주 개수, 예상 도착일, 반영 재고·입고량, 예상 매입액, 적용 가정, 계산 버전.
- 재고 미입력 상품은 계산 대상에서 제외합니다. 예측 범위 밖의 수요가 필요한 경우에도 조용히 외삽하지 않습니다.
- 상품별 납기와 만료 시점을 반영합니다. 입고 전의 판매로 줄어드는 재고와 만료되는 재고는 도착 후 사용 가능 수량에서 제외합니다.
- 개수는 최종적으로 0 이상의 정수입니다. 묶음 주문·최소 주문량이 필요하면 적용 방식과 반올림 규칙을 함께 확정합니다.
- 사용자가 숫자를 바꿔 저장할 수 있습니다. 원래 추천량과 수정량을 구분합니다.
- 완료 조건: 같은 입력과 버전에서 같은 결과가 나오고, 계산에 반영한 값과 불가 사유를 확인할 수 있습니다.
- 답변 대기: 질문 18~21의 만료·납기·발주 주기·예측 범위 초과 처리.

계산 방법은 [6. 발주 계산 설계](#6-발주-계산-설계-제안)를 따릅니다.

### F09. 발주안 수정·저장·내보내기 — 요구 확정, 형식·권한 미정

- 수정: 추천량과 별도로 최종 수량을 입력하고 예상 매입액을 다시 계산합니다.
- 저장: 매장·상품·도착일·작성자·최종 수량·당시 추천과 계산 조건을 함께 보관합니다.
- 추적: 예측 버전, 재고 기준, 날씨 기준을 저장해 나중에 최신 결과와 혼동하지 않게 합니다.
- 예측·재고·납기가 바뀌면 기존 안은 당시 기준의 기록으로 남기고 재계산 필요를 표시합니다.
- 내보내기 항목안: 매장, 공급사, 작성일, 도착 예정일, 상품 ID·이름, 수량, 개당 원가, 합계, 단위.
- 파일에 미계산 상품을 추천 0개로 넣지 않습니다. 제외 상품과 이유를 내보내기 전에 확인합니다.
- 저장·내보내기가 공급사 실제 주문 완료를 의미하지 않습니다.
- 완료 조건: 다시 열어도 저장한 값이 유지되고, 파일의 수량·금액이 확정한 값과 일치합니다.
- 답변 대기: CSV·Excel·PDF 형식, 초안·최종 확정 상태, 직원 권한, 공급사별 파일 분리.

### F10. 과거 재생·모델 비교 — 과거 재생 요구 확정, 지표 구성은 제안

- 기준 날짜를 바꾸며 당시까지 확보된 판매 기록으로 이후 7일 예측을 확인합니다.
- 이후 실제 판매량은 결과 비교에만 사용하고 예측 입력에서는 가립니다.
- 비교안: 동일 요일 기준선, 날씨 없는 모델, 날씨 포함 모델. TFT는 학습·검증한 경우에만 추가합니다.
- 출력안: 수량 MAE, 분위수 손실, 예측 구간 포함률, 기간·매장·상품별 표본 수.
- 발주 정책 비교는 같은 초기 재고·입고·가격·만료 가정과 같은 평가 구간을 사용합니다.
- 완료 조건: 평가 기간·자료 출처·날씨 종류·실험 가정과 결과를 함께 확인할 수 있습니다.
- 공개 자료에 실제 재고·품절·폐기 기록이 없다면 관련 결과는 **시뮬레이션 추정치**입니다.
- 날씨 포함 모델의 개선이 없거나 기준선이 더 좋으면 그 결과를 그대로 표시합니다.

### F11. 알림·날씨 변경 시나리오 — 답변 대기

- 알림 후보: 재고 입력 필요, 예측 갱신, 발주안 재계산 필요. 전달 채널은 질문 31에서 결정합니다.
- 시나리오 후보: 기온·강수 가정을 바꿔 예측을 비교합니다. 포함 우선순위는 질문 32에서 결정합니다.
- 시나리오는 실시간 예보와 분리하고, 모델 반응을 실제 인과 효과·확정 매출 증가로 설명하지 않습니다.
- 현재 필수 기능으로 승인되거나 구현된 상태가 아닙니다.

## 5. 데이터와 시간의 공통 규칙

### 5.1 최소 데이터 구조 제안

| 대상 | 주요 항목 |
| --- | --- |
| 매장 | ID, 이름, 위치, 시간대, 화폐 단위, 영업일, 판단 기준 시각 |
| 소속 | 계정 ID, 매장 ID, 점주·직원 역할 |
| 상품 | ID, 매장 ID, 이름, 개수 단위, 가격·원가, 공급사, 납기, 판매 가능 기간 |
| 일별 판매 | 매장 ID, 상품 ID, 현지 판매일, 판매 개수, 입력 출처·시각 |
| 재고 확인 | 매장 ID, 상품 ID, 수량 또는 미확인, 실사 시각, 만료 정보 |
| 입고 예정 | 상품, 수량, 도착 예정, 반영 상태, 연결한 발주안 |
| 날씨 자료 | 위치, 적용 날짜, 관측·예보 구분, 제공처, 발표·이용 가능·조회 시각 |
| 예측 실행 | 매장, 기준 시각, 판매·날씨 자료 버전, 모델 버전, 날짜별 예측 |
| 발주 계획 | 매장, 작성자, 상태, 상품별 도착일·추천량·수정량, 계산 기준 |
| 데이터 출처 | 원본 자료명·기간·지역·화폐·라이선스, 실제·가상·수동 입력 구분 |

DB 제품과 실제 테이블/API 형식은 아직 정하지 않았습니다.
서로 다른 매장에서 같은 상품 ID 문자열을 써도 매장까지 포함해 식별합니다.
해외 판매 기록은 원본 시간대·단위를 유지하고 국내 가상 매장 자료와 구분합니다.

### 5.2 공개 자료와 가상 값

- 현재 확보 상태는 ‘공개 자료만 있음’입니다. 최종 데이터셋과 원본 파일 점검은 미완료입니다.
- 식품·상품별 **개수**·여러 매장·일자·지역의 확인 가능 여부를 우선 점검합니다.
- 주간 부서별 매출액, 메뉴 매출액, 합성 수요 예측값을 실제 상품별 일일 판매 개수와 섞지 않습니다.
- 원본에 재고·원가·납기·유통기한이 없다면 실제 측정값처럼 채우지 않습니다.
- 샘플 상품명·비용 등 가상 값을 쓰면 가상임을 표시합니다. 재고는 질문 17의 결정대로 사용자가 입력하기 전까지 비워 둡니다.
- 사용자가 입력한 체험용 재고는 원본 공개 자료의 실측 재고가 아닙니다.
- 오래된 해외 판매 기록의 날짜·지역만 국내 현재로 바꾸어 실제 국내 예측 성능으로 발표하지 않습니다.
- 파일 공개·재배포 전에 선택한 자료의 이용 조건을 확인합니다. 현재 데이터셋 선정이나 대량 다운로드를 완료했다고 가정하지 않습니다.

질문 30의 제안은 ‘공개 자료의 성능 검증’과 ‘가상 매장의 실시간 날씨 체험’을 구분하는 방식입니다.
사용자 답변 전 두 모드를 확정하지 않습니다.

### 5.3 과거 날씨 검증

과거 재생에서 어떤 시점에 어떤 정보가 알려져 있었는지 기록합니다.
판매 마감 뒤 집계되는 값과 미래 관측 날씨를 과거 발주 시점의 입력으로 사용하지 않습니다.
당시 예보가 없으면 미래 관측 날씨를 사용한 참고 실험으로 표시합니다.

Open-Meteo Historical Forecast API는 각 예보 실행의 초반 시간을 이어 붙인 시계열입니다.
그 자체를 ‘특정 과거 시점에서 발급된 7일 예보’로 사용하면 안 됩니다.
전체 예측 기간이 필요한 경우 개별 실행 자료와 이용 가능 시점을 확인해야 합니다.
출처: [Historical Forecast API](https://open-meteo.com/en/docs/historical-forecast-api).

Single Runs의 모델 초기화 시각도 실제 공개 시각과 다릅니다.
과거 주문 시각 전에 공개된 자료인지, 대상 날짜가 보관 범위에 있는지,
과거 운영 예보인지 나중에 재생성한 hindcast인지 확인합니다.
출처: [Single Runs API](https://open-meteo.com/en/docs/single-runs-api).

## 6. 발주 계산 설계 제안

다음은 질문 18~21 답변 후 구현할 정책의 설계안입니다.
유통기한·납기·발주 주기를 정하지 않은 상태에서 정확한 최적 발주량을 약속하지 않습니다.

### 6.1 계산 전 확인

1. 재고를 직접 입력했는지, 확인 시각이 무엇인지 검사합니다.
2. 입고 예정과 없는 경우의 확인 상태를 검사합니다.
3. 가격·원가, 납기, 판매 가능 기간, 발주 주기가 정해졌는지 검사합니다.
4. 재고 소비·입고·만료를 계산할 모든 날짜에 예측이 있는지 검사합니다.
5. 부족한 조건은 상품별로 안내하고 해당 발주량을 비워 둡니다.

당일 도착·시간 단위 발주를 지원하면 당일 잔여 수요도 필요합니다.
이를 다음 날부터의 예측으로 대신하지 않습니다. 지원 여부와 날짜 경계는 별도 확정합니다.

### 6.2 여러 날 재고 처리

- 설계 제안은 날짜별 입고 → 판매 가능 여부 확인 → 판매에 따른 재고 소비 → 만료 처리입니다.
- 정확한 만료일의 시작·종료 시각과 사용 순서는 질문 18에서 확정합니다.
- 배치별 관리를 선택하면 먼저 만료되는 재고부터 사용합니다.
- 새 주문이 도착하기 전의 기존 재고 소진, 예정 입고, 도착 후의 판매 가능 기간을 반영합니다.
- 여러 날의 수요는 기간합을 직접 예측하거나 검증한 수요 시나리오로 계산합니다. 일별 P90을 더해 기간 P90이라고 부르지 않습니다.
- 기간 마지막에 남았다는 이유만으로 아직 판매 가능한 재고를 전량 폐기 처리하지 않습니다. 평가 종료 시 잔여 가치를 어떻게 다룰지도 고정합니다.

최종 추천은 후보 주문량의 비용을 비교하는 방식부터 검증합니다.
서로 다른 유통기한과 납기를 무시한 `7일 판매 예측 합계 - 현재 재고`를 일반 발주 공식으로 사용하지 않습니다.

### 6.3 비용 기준

판매가를 p, 개당 매입 원가를 c라고 할 때 제안하는 비교 기준은 다음과 같습니다.

`추정 손실 = 폐기 개수 × c + 미충족 수요 개수 × (p - c)`

이는 폐기 회수액·폐기 처리비·재고 보관비를 추가 입력받지 않는 상황의 단순화입니다.
시뮬레이션에서는 이 비용을 0으로 가정했음을 명시하고, 다른 비용을 측정했다고 주장하지 않습니다.
매입원가가 이미 폐기 손실에 들어가므로 매입 비용을 같은 손실식에 중복해서 더하지 않습니다.
비교 기간 마지막의 유효 재고와 기간 밖의 도착 주문도 같은 기준으로 정산합니다.

부족 손실은 전체 판매가가 아니라 놓친 공헌이익 p-c를 기본값으로 제안합니다.
실제 품절 수요가 관측되지 않으면 ‘미충족 수요’도 수요 시나리오에 따른 추정치입니다.

폐기와 품절의 비용을 함께 비교하되, 어떤 가중치가 가장 적절한지는 실제 자료로 검증해야 합니다.
특정 분위수 하나가 여러 기간의 재고 문제를 항상 최적화한다고 설명하지 않습니다.

## 7. 모델 학습·평가·전달

### 7.1 학습과 선택

1. 선택한 자료가 상품별 수량 예측에 맞는지 점검합니다.
2. 시간순으로 학습·검증·최종 테스트를 분리합니다. 같은 미래 날짜가 섞이지 않게 합니다.
3. 요일 기준선을 만들고, 같은 입력 마감 조건으로 LightGBM을 비교합니다.
4. 날씨 포함·제외 모델을 비교해 날씨 기능의 추가 효과를 확인합니다.
5. 시간과 자료가 충분하면 TFT를 비교합니다. 더 어려운 모델이라는 이유만으로 채택하지 않습니다.
6. 마지막 테스트 구간은 모델·정책 선택에 반복 사용하지 않습니다.

여러 날 앞을 예측할 때 각 기준 시점 이후의 실제 판매량이 lag·이동평균에 섞이지 않게 합니다.
P10~P90 구간의 포함률은 별도 측정하며, 이름만으로 80% 포함을 보장하지 않습니다.
판매량 0은 수요 0·품절·단종 중 어느 하나로 자동 확정하지 않습니다.
수요가 가려진 자료로 실제 폐기 감소·품절 감소·매출 증가를 입증했다고 발표하지 않습니다.

## 8. 공통 상태·완료 기준

| 상태 | 사용자에게 보여줄 내용 |
| --- | --- |
| 재고 미입력 | 예측은 표시, 발주량은 `—`, 직접 입력으로 연결 |
| 일부 상품만 계산 가능 | 계산된 상품 수·제외 이유, 부분 합계 표시 |
| 판매 이력 부족 | 필요한 조건과 현재 이력, 지원 가능한 기준선 여부 |
| 날씨 실패·부분 누락 | 적용 범위·조회 실패·캐시 시각, 계산 가능 여부 |
| 모델 실패 | 실패 안내, 이전 결과가 있으면 생성 시각과 이전 결과임을 표시 |
| 파일 오류·중복 | 행·열·원인, 확인 전 저장하지 않은 상태 |
| 저장 충돌·실패 | 저장되지 않았음을 표시, 사용자 수정 값을 유지 |
| 권한 없음 | 대상 매장 자료를 반환하지 않고 접근 안내 |
| 계획 기준 변경 | 당시 계산 기준 표시, 재계산 필요 안내 |

모든 수량·금액에 단위를 붙입니다. 빈 값과 0을 구분합니다.
저장·오류 상태를 색상만으로 전달하지 않고 문구를 함께 씁니다.
주요 입력과 저장은 키보드로 사용할 수 있게 구성합니다.
브라우저에 서버용 API 비밀값을 노출하지 않습니다.
내보내기에서 상품명 등 사용자 텍스트가 스프레드시트 수식으로 실행되지 않게 처리합니다.

파일 한도·응답 시간 목표·데이터 보관·삭제·체험 자료 초기화·여러 사용자의 동시 편집 정책은 아직 미정입니다.
실제 구현 시 선택한 범위에 필요한 오류 처리와 완료 기준을 함께 검증합니다.
