# 화개장날 3분 시연 안내

점주 업무를 끝까지 처리한 뒤 실제 TFT 추론을 보여줍니다.
현재 동작은 [구현 현황](implementation.md)을 기준으로 하며, [기능 명세서](functional-spec.md)는 초기 요구·설계 기록입니다.

## 두 시연 경로

| 화면 | 자료·계산 | 보여줄 가치 |
| --- | --- | --- |
| 매장 요약·판매 기록·재고 확인·발주 계획 | 초기 2매장·각 10상품·84일 가상 판매, 날씨 미사용 요일 기준선 | 판매 입력부터 재고 확인·수정·확정·파일까지 이어지는 점주 업무 |
| TFT 모델 체험 | Walmart 실제 과거 표본, 56일 입력 → 7일 예측, 준비된 체크포인트의 실제 CPU 추론 | 공개 자료로 학습한 신경망을 웹에서 실행하고 같은 입력의 기준선과 비교 |

실시간 날씨가 보인다는 사실이 일반 매장의 예측에 날씨가 반영된다는 뜻은 아닙니다.
TFT의 미래 날씨는 마지막 관측값을 7일 유지하는 `persistence`입니다. 당시 발급 예보를 사용한 예측은 아닙니다.
TFT 시연 결과는 현재 매장·발주 DB에 저장하지 않습니다.

## 시작 전 준비

1. 점주 계정으로 로그인합니다. 로컬 기본 샘플은 **점주 체험** 버튼을 사용할 수 있습니다. 운영 로그인 정보는 배포 담당자가 별도로 관리합니다.
2. 사용할 매장·상품 하나를 정하고 현재 판매 기록을 확인합니다. CSV의 `date,product_id,units_sold`는 기존 자료와 중복되지 않는 행으로 준비합니다. 오늘 이후 날짜·소수 판매 개수는 사용할 수 없습니다.
3. 선택 상품의 판매가가 원가보다 높고 `납기 + 발주 주기 - 1 ≤ 7`인지 확인합니다. 재고 미입력과 직접 확인한 0개의 차이를 보여줄 수 있도록 준비합니다.
4. 시연 당일의 재고·만료일·입고 예정 입력값을 준비합니다. 과거 날짜로 저장된 재고는 오늘 다시 확인해야 합니다.
5. **TFT 모델 체험**에서 **상태 다시 확인**을 눌러 준비 완료인지 확인하고 실제 예측을 한 번 실행합니다. 설정은 [모델 규약](model-contract.md)을 따릅니다. `/health` 성공만으로 TFT 준비 완료를 판단하지 않습니다.
6. 다운로드 저장 위치와 화면 크기를 확인합니다. 리허설은 승인된 시연 매장 또는 별도 로컬 DB에서 진행하며 운영 DB를 지워 초기화하지 않습니다.

초기 샘플은 DB를 처음 만들 때 생성됩니다. 리허설에서 저장한 판매·재고·발주가 다음 실행에도 남을 수 있으므로 같은 CSV를 반복 저장하지 않습니다.
일반 매장의 `FORECAST_PROVIDER`는 비워 두고, 별도 TFT 환경만 설정합니다.

## 3분 진행표

| 시간 | 화면과 조작 | 설명 |
| --- | --- | --- |
| 0:00–0:20 | 매장 요약에서 예측·재고 미입력 상태 확인 | “예상 판매량과 추가 발주량은 다릅니다. 재고를 확인하기 전에는 발주 개수를 임의로 만들지 않습니다.” |
| 0:20–0:50 | 판매 기록 → CSV 미리보기 → 유효 행 확인 → 저장 | “누락을 판매 0개로 바꾸지 않고, 잘못된 값과 중복을 검사합니다. 이 가상 매장의 예측은 요일 기준선입니다.” |
| 0:50–1:30 | 재고 확인 → 수량·만료일·입고 예정 입력 → 발주 계산 | “사용 가능한 재고, 도착까지 걸리는 시간, 판매 기간과 가격·원가를 함께 반영합니다.” |
| 1:30–2:00 | 발주 계획 → 추천 수량 조정 → 초안 저장 → 점주 확정 → Excel 다운로드 | “추천값은 점주가 조정하고 최종 결정은 파일로 남깁니다. 공급사 주문이 자동 전송되는 단계는 아닙니다.” |
| 2:00–2:50 | TFT 모델 체험 → 실제 실행 → 상품 2개 전환 → 그래프·수량 표 확인 | “별도 화면에서는 Walmart의 실제 과거 자료로 학습한 TFT를 실행합니다. 56일 입력으로 다음 7일을 예측합니다. 마지막 관측 날씨가 이어진다는 가정입니다.” |
| 2:50–3:00 | 모델·자료 출처와 범위 표시 | “근거를 확인하고 발주 결정을 완료하는 흐름을 만들었습니다. 한국 점포 데이터와 실제 예보로 추가 검증하는 것이 다음 단계입니다.” |

수량·매입액은 화면의 실제 계산값을 읽습니다. 특정 추천 개수나 응답시간을 미리 보장하지 않습니다.
판매·재고·상품 설정을 바꾼 뒤에는 다시 계산한 발주안으로 저장·확정합니다.

## 질문받았을 때 설명할 범위

- **날씨 덕분에 정확도가 좋아졌나?** 현재 별도 TFT는 과거 관측과 persistence를 사용합니다. 날씨 제외 TFT·현재 API 기준선과 동일 테스트 구간에서의 비교는 후속 검증입니다.
- **차트에서 TFT가 기준선보다 높으면 더 좋은가?** 예측값이 다르다는 뜻입니다. 시연 입력에는 미래 판매 정답이 없어 이 화면에서 오차·성능 우열을 계산하지 않습니다. 오프라인 평가 범위는 [ML 평가 기록](../ml/evaluation.md)을 따릅니다.
- **P10~P90이면 정확도 80%인가?** 모델의 분위수 범위입니다. 실제 포함률은 별도 평가해야 하며 해당 범위를 정확도나 보장으로 설명하지 않습니다.
- **실제 수요·폐기·이익 개선을 증명했나?** 관측 판매량이 품절로 놓친 수요 전체를 나타내지는 않습니다. 실제 한국 점포 수요와 폐기·이익 개선은 아직 검증하지 않았습니다.
- **발주량이 최적인가?** 현재는 고정 수요 3경로의 비용 비교를 이용한 근사 계획입니다. 실제 재고·납기·만료·원가 가정에 따라 결과가 달라집니다.

## 실패 시 복구

| 증상 | 대응 |
| --- | --- |
| 로그인 만료·권한 오류 | 다시 로그인하고 점주 계정인지 확인합니다. 직원은 최종 확정·내보내기를 할 수 없습니다. |
| CSV 중복·형식 오류 | 오류 행을 확인합니다. 기존 값을 덮어쓰지 않고 저장하지 않은 준비 행으로 교체합니다. 미리보기만으로는 DB에 저장되지 않습니다. |
| 재고 미입력·오래된 재고 | 오늘 수량·만료일·입고 예정을 확인하고 저장한 뒤 다시 계산합니다. 재고 없음은 직접 확인한 0개로 입력합니다. |
| 계산 기준 변경 안내 | 최신 판매·상품·재고로 다시 계산하고 새 초안을 저장합니다. 이전 계산을 억지로 확정하지 않습니다. |
| 날씨 조회 실패·오래된 캐시 | 화면의 상태·시각을 그대로 설명합니다. 날씨를 사용하지 않는 일반 매장 기준선의 업무 흐름을 계속 시연할 수 있습니다. |
| TFT 준비 중 | 잠시 후 **상태 다시 확인**을 누릅니다. 준비 전 반복 실행하지 않습니다. |
| TFT 환경 없음 | 배포 담당자가 모델 Python·체크포인트 설정을 확인합니다. 변경 후 API를 다시 시작하고 준비 상태를 확인합니다. |
| TFT 연결 실패·시간 초과 | API 로그와 모델 환경을 확인하고 API를 다시 시작합니다. 복구가 늦으면 점주 업무 흐름으로 시연을 마무리하고 모델 실행 장애를 설명합니다. |
| API 연결 자체가 안 됨 | 웹·API 프로세스, 주소와 포트, 로컬 CORS 설정을 확인합니다. 운영에서는 배포 담당자가 서비스 상태를 확인합니다. |

저장된 예상 JSON, 스크린샷이나 기준선을 현재 TFT가 실행한 결과로 표시하지 않습니다.
복구용 서버 절차와 배포 되돌리기는 [배포 안내](deployment.md)를 따릅니다.
