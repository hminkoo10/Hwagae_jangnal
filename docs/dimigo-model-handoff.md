# 디미고 매점 실데이터 TFT — 모델 담당 작업 지시

디미고사회적협동조합 매점의 실제 POS 판매(2025-10-01~2026-10-24)로 TFT를 학습해 `ml/merchant_tft/`의 합성 학습 모델을 교체합니다. 발표에서는 학습에 쓰지 않은 뒤 30% 기간을 앱에 올려 시연·평가합니다.

## 1. 받는 자료

`1_모델담당_70%학습.zip` 하나만 받습니다. 열 정의는 안에 있는 `README.txt`를 봅니다.

| 파일 | 내용 |
| --- | --- |
| `sales_daily.csv` | 상품×일 판매 개수 83,205행, 449개 상품 |
| `products.csv` | 이름·종류(이름 규칙으로 분류한 추정값)·기간·대표 판매가 |
| `weather_daily.csv` | 안산 와동 일별 최고/최저 기온·강수, Open-Meteo 과거 재분석 |
| `split.json` | 원본 해시·기간·분할 규칙 |

- 학습 기간: **2025-10-01 ~ 2026-07-11**, 판매일 223일(70%)
- 평가 기간: 2026-07-12 ~ 2026-10-24, 판매일 96일(30%). **모델을 제출할 때까지 받지 않습니다.** 제출 후 웹/API 담당이 평가하고 원본을 공개합니다.
- 원본 POS 자료입니다. Git, 공개 저장소, Colab 공개 노트북에 올리지 않습니다.

## 2. 자료를 해석하는 규칙

- 상품의 첫 판매일과 마지막 판매일 사이에 판매 행이 없는 날은 **실제 0개**입니다. POS는 판매한 상품만 기록합니다. 이 기간 밖의 날은 자료에 없으므로 0으로 채우지 않습니다.
- `store_has_sales=0`은 매장 전체에 판매가 없던 날(휴무·방학)입니다. 앱이 추론할 때는 이 값을 주지 않습니다. 그러므로 **모델 입력 특징으로 쓰지 않습니다.** 분석이나 학습 손실 가중치에만 씁니다.
- `est_stock_open`은 발주 누적 − 판매 누적으로 추정한 영업 시작 재고입니다. 발주 기록이 판매와 맞는 154개 상품만 있습니다. 값이 0이고 판매도 0인 행(약 6천 행)은 품절이라 못 판 날일 수 있습니다. 손실에서 빼거나 가중치를 낮추는 것을 권합니다. 이 값도 추론 때는 없으니 입력 특징으로 쓰지 않습니다.
- 이름만 바뀐 POS 상품은 하나의 `product_id`로 합쳤습니다. 예: `쿠) 미에로화이바350ml` → `미에로화이바350ml`.
- 주말 판매는 평일의 1/4~1/10이고, 겨울방학(2026-01-24~02-18)에는 판매가 거의 없습니다. 학사일정은 넣지 않기로 했습니다. 요일·연중 달력·과거 판매·날씨만 씁니다.

## 3. 모델 규약 — 지금 앱 연결 그대로

[모델 연결 규약](model-contract.md)의 일반 매장 경로와 `ml/merchant_tft/README.md`를 따릅니다. 입출력을 바꿔야 하면 먼저 협의합니다.

- `predict(context) -> dict`. context는 API의 일반 매장 입력입니다(`ml/merchant_tft/smoke.json` 참고).
- encoder: 최근 연속 **56일** 판매 + 달력. decoder: 달력 + `weather.days`의 `temp_max`·`temp_min`·`rain_mm`. 예측은 **7일**입니다.
- 분위수 **0.10/0.25/0.50/0.75/0.90**으로 학습합니다. API에는 상품별 `date,p10,p50,p90`만 반환합니다.
- store/product ID를 embedding으로 쓰지 않습니다. 시연 매장의 상품 코드는 같지만, 다른 매장에도 같은 모델을 씁니다. 정적 범주는 context에 있는 `category`만 선택적으로 씁니다. 처음 보는 종류도 처리해야 합니다.
- 정규화는 입력 56일만으로 계산합니다. 추론 중에 fit·학습·다운로드하지 않습니다. 56일 중 누락이 있으면 `insufficient_history`를 반환합니다.
- 학습 날씨는 실제 관측(재분석)이지만 앱은 발급된 예보를 입력합니다. 기존 merchant 모델처럼 decoder 날씨에 예보 오차 잡음을 넣는 것을 권합니다.
- CPU float32, `ml/requirements-inference.txt`(Python 3.11, torch 2.11 CPU, pytorch-forecasting 1.5.0)에서 동작해야 합니다. 50개 상품 추론이 수 초 안에 끝나야 합니다. state_dict만 저장하고 `torch.load(weights_only=True)`로 읽습니다.

## 4. 검증 — 70% 안에서만

- 학습 기간 안에서 시간순으로 나눕니다. 예: 마지막 약 6주(2026-05-30~07-11)를 검증으로 써서 epoch과 설정을 고릅니다. 날짜를 섞어 나누지 않습니다.
- 같은 검증 창에서 API 요일 기준선(`apps/api/app/forecasting.py`의 `baseline`)과 비교합니다. MAE, 5분위 pinball, P10~P90 포함률, 구간 폭을 보고합니다.
- 날씨 제거 모델 비교는 선택입니다. 하더라도 seed와 환경을 같게 맞춥니다.

## 5. 제출물

`ml/merchant_tft/` 안의 파일만 바꾸는 PR 하나로 냅니다. `apps/`는 수정하지 않습니다.

- `train.py`, `network.py`, `predict.py`, `model.ckpt`, `manifest.json`, `training-log.json`, `expected-api.json`, `smoke.json`, `README.md`
- `manifest.json`에 넣을 것:
  - `model.training_data: "dimigo_store"`
  - `model.note`: 학습 자료와 기간, 검증 범위
  - 학습/검증 기간, seed, 패키지 버전, 체크포인트 SHA-256, 검증 지표(기준선과 함께)
- `ml/tests/test_merchant_tft.py`가 새 모델로 통과해야 합니다. 학습 원본 자료는 PR에 넣지 않습니다.
- PR 본문에 학습 환경(Colab GPU 등)과 CPU 재현 결과(`expected-api.json` 비교)를 적습니다.

## 6. 웹/API 담당이 하는 일

- 원본 변환: `scripts/make-dimigo-data.py`. 70%/30% 분할, 상품명 합치기, 발주 기반 재고 추정, 날씨 수집을 합니다.
- 제출 모델을 30% 기간에서 평가합니다. 기준일을 굴려 가며 7일씩 예측하고 요일 기준선과 비교합니다. Walmart 평가 수치와 섞지 않습니다.
- API가 `training_data: "dimigo_store"`를 받도록 바꾸고 화면의 모델 설명 문구를 바꿉니다.
- 시연 파일은 발표 전날 다시 만듭니다. 요일을 유지하도록 7일 단위로 날짜를 옮깁니다.

```powershell
uv run python scripts/make-dimigo-data.py --orders <구매현황 XLSX> --sales <판매현황 XLSX> --output <폴더> --demo-date <시연일>
```

시연 재고는 실사가 아니라 발주 기록으로 추정한 값입니다. 화면과 발표에서도 그렇게 말합니다. 원가는 발주 단가이고, 납기·발주 주기·유통기한·거래처명은 가정값입니다.
